Paste the headers. See who really sent it.

A suspicious email is a routing question before it is anything else. These headers record every server that touched the message, what the receiving server concluded about SPF, DKIM and DMARC, and whether the From address agrees with the envelope it arrived in. This page reads that record and points at the disagreements.

Nothing leaves the browser. There is no upload, no fetch and no analytics on this page — the analysis runs in the tab. That matters when the input is a real email.

How it works

An email has two identities. The envelope is what the mail servers use to route and bounce it: the Return-Path and the Received chain. The letter is what your mail client shows you: From, Reply-To, Subject. Spoofing works by making the second one convincing while the first says something else.

The page does six things, in order:

  1. Unfolds the headers. A header may be wrapped across several lines (RFC 5322 folding). Received headers almost always are, usually in the middle of an address or a timestamp.
  2. Rebuilds the route. Received headers are written newest-first, so they are reversed to show the message travelling from its first server to your inbox, with the delay between each hop.
  3. Reads the authentication report. SPF, DKIM and DMARC results are taken from Authentication-Results, which the receiving server adds after it has checked them.
  4. Compares the identities. From against Return-Path, Reply-To, Sender, Message-ID and the first hop — comparing registrable domains, so mail.example.co.za and example.co.za are the same site.
  5. Flags the specific tricks. A display name containing a different address, a punycode From domain, an invented Date, hop timestamps that run backwards.
  6. Writes it out. Every finding gets a sentence explaining what it means and how much weight to give it — including the ones that are usually innocent.

Nothing is scored out of ten. A number would imply a certainty this data does not support; the verdict is only ever consistent, mixed or suspicious, and each of those is defined by the findings below it.

What this cannot tell you

  • It does not re-check anything. No DNS lookups, no signature verification. It reports what the receiving server recorded. If that server lied, or never checked, this page cannot tell.
  • Headers can be forged. Everything above the last trusted Received line is written by whoever sent the message. Your provider's own hop is the only one you can take at face value, which is why the route is shown from the bottom up.
  • Authentication passing is not the same as safe. A phishing site can register a lookalike domain and configure SPF, DKIM and DMARC perfectly. The checks prove the domain sent it, not that the domain is honest.
  • No IP reputation or geolocation. The page makes no network requests, so it cannot say whether a sending IP is on a blocklist or where it is.
  • Domain comparison is approximate. It uses a short list of two-label suffixes such as co.za and co.uk, not the full Public Suffix List.
  • One message is not a campaign. A single suspicious header is a reason to check through another channel, not a conclusion about the sender.

If it does look wrong

  1. Do not use the links or the phone number in the message.
  2. Reach the organisation through a channel you already trust — the number on your card, the app, or the website you type yourself.
  3. Report it: in Gmail, Report phishing; in Outlook, Report → Phishing. That is what feeds the filters that protect everyone else.
  4. If you already entered credentials, change that password and any place it was reused, then turn on two-factor authentication.
